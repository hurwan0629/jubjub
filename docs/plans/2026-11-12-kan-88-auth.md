# KAN-88 로그인·인증 API

범위: 기존 FastAPI 구조에 JSON 로그인, 관리자 회원가입, JWT 인증 의존성,
관리자 시드 명령을 추가해요. 기존 users 테이블을 사용해요.
사용자의 후속 요청에 따라 프로젝트의 정식 관리자 회원가입으로 제공해요.

## 계약

- POST /auth/register: loginId, password, name, phone, email → 201. 아이디·이메일 중복은 409.
- POST /auth/login: loginId, password → accessToken, tokenType, expiresIn, isFirstLogin.
- isFirstLogin = not route_setup_done. 로그인 자체는 설정 완료 상태를 바꾸지 않아요.
- 잘못된 계정·비밀번호는 같은 401 안내를 반환해요.
- Argon2 해시, HS256 JWT, sub/iat/exp 필수, 토큰 기본 수명 60분.
- GET /me와 이후 업무 라우터는 공통 인증 라우터에 등록해요.
- health, 문서, 로그인·가입은 공개예요. 가입은 별도 활성화 설정 없이 제공해요.
- 시드는 같은 입력 검증·해시·중복 처리 서비스를 사용하고 비밀번호를 숨겨 입력받아요.
- 앱 로그인 화면 연결과 경로 설정 완료 API는 별도 작업이에요.

## 구현 및 검증 순서

1. 실제 SQLAlchemy 세션을 쓰는 격리 SQLite 테스트로 가입→로그인→인증 흐름을 먼저 작성해요.
2. 스키마, Argon2/JWT 도구, 서비스, 인증 의존성, 라우터를 구현해요.
3. 시드 명령과 실행 안내, 환경변수·패키지 버전을 추가해요.
4. 전체 pytest, Ruff, Alembic check를 실행하고 완료 조건을 대조해요.

## 검토 초점

- 위조·만료·누락 클레임·다른 알고리즘·삭제된 사용자 토큰은 401이에요.
- 비밀번호·해시는 응답과 JWT에 포함하지 않아요.
- 로그인 실패와 성공 모두 경로 설정 상태를 변경하지 않아요.
- 중복 가입 트랜잭션은 rollback하고 기존 계정은 유지해요.
- JWT 키가 비어 있거나 기본값이면 토큰을 발급하지 않아요.
- 실제 Supabase에 테스트 계정을 남기지 않아요.

## 완료 기록

- 가입 API가 없어 404로 실패하는 테스트를 확인한 뒤 구현했어요.
- 로그인·가입·JWT·시드와 기존 API를 포함한 테스트 37개가 통과했어요.
- Ruff check/format, git diff --check 통과. Alembic check 변경 사항 없음.
- 실제 Supabase에서 가입 201, 로그인·인증 조회 200, 중복 409,
  잘못된 비밀번호·토큰 누락 401, 설정 상태에 따른 첫 로그인 분기를 확인했어요.
- 실제 DB 검증은 외부 트랜잭션을 롤백했고 테스트 계정이 남지 않았음을 확인했어요.
- 별도 코드 리뷰에서 주요 결함이 발견되지 않았어요.
- 로컬 .env에 없던 JWT 서명 키를 무작위로 생성했어요. 값은 출력·커밋하지 않았어요.
- 기존 users 모델·마이그레이션 작업을 유지했고 커밋·푸시·Jira 변경은 하지 않았어요.
