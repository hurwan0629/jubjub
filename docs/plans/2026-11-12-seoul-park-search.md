# C-03 서울 공원 검색 API

사용자는 서울 전체 범위를 선택했어요. 서버에서 OSM 경계를 일괄 정제하고 Supabase 검색 목록에 저장해요.
네이버 장소 검색 비밀키는 사용하지 않아요. 이름·주소 검색은 저장한 데이터에서 처리해요.
Figma C-03 검색 결과(199:2749)와 현재 앱 Park 타입을 확인했어요.

- GET /parks: JWT 필수, query(이름·주소), 선택적 latitude/longitude(둘 다 필수), limit/offset.
- 응답은 기존 Park[]: 문자열 id, name/address/distance, bounds(southWest/northEast), area(outer/holes).
- 사용자 위치가 없으면 distance는 빈 문자열. 있으면 공원 대표점까지 직선거리로 정렬·표시해요.
- 빈 검색어는 위치가 있을 때만 근처 공원을 반환해요. 위치와 검색어가 모두 없으면 빈 배열이에요.
- 검색용 park_catalog_entries는 운영 parks(설계서의 공원 1곳)와 분리해요. 선택 ID는 목록 PK로 유지해요.
- OSM way·relation을 검증해요. 닫히지 않거나 유효하지 않은 경계는 거부하고 결과 보고서에 남겨요.
- relation의 outer/inner를 합치고 구멍을 보존해요. 분리된 polygon은 명확히 이름 붙인 구역별 항목이에요.
- 원본이 같은 source_key로 다시 적재하면 같은 PK를 유지해요. 원본 주소가 없으면 미등록으로 표시해요.
- 모든 행에 원본 URL·라이선스·수집 시각을 저장하고, 정규화 데이터와 출처 안내를 배포해요.
- OSM 등록 데이터 범위이므로 서울의 모든 공식 공원을 빠짐없이 보장하지는 않아요.

## 작업 순서

1. 격리 DB API 테스트, 합성 OSM 경계 정제 테스트를 먼저 작성하고 실패를 확인해요.
2. 목록 모델·마이그레이션·JWT 라우터·검색 서비스를 구현해요.
3. OSM 수집·정제 명령과 반복 적재 명령을 구현해요.
4. 실제 서울 데이터를 검증·적재하고 인증 검색·홀 보존·재적재 안정성을 확인해요.
5. 전체 pytest/Ruff/Alembic 검사, 별도 코드 리뷰와 프론트 전달 문서를 작성해요.

## 프론트 전달 범위

현재 로컬 client.ts에는 SERVER_READY가 없고 로그인 UI도 임시 동작이에요.
백엔드 구현과 데이터 적재를 우선하고, 프론트 코드를 임의로 전환하지 않아요.
인증 연결 후 parks만 서버 사용하도록 팀원에게 계약을 전달해요.
내 위치 버튼의 고정 한강 검색은 위치 권한을 얻어 latitude/longitude 요청으로 바꿔야 해요.

## 검증 기록

- 이름·주소·위치 검색, 인증, 페이지, 원본 다각형·구멍, 부분 입력 거부, 반복 적재 테스트 통과.
- 실제 서울 25개 자치구와 공원 원본을 수집했고 경고가 있는 1개 relation은 제외했어요.
- Supabase 마이그레이션 적용, 유효 검색 구역 2,322개 적재, RLS 확인.
- 실제 API에서 여의도 3개 결과와 내부 구멍, 영등포구 59개 결과, 거리 계산을 확인했어요.
- 실제 재적재 후 전체 PK 유지와 검증 계정 롤백을 확인했어요.
- 리뷰에서 구역 면적 순위가 바뀔 때 식별자가 바뀌는 문제를 재현했어요.
  회귀 테스트를 먼저 실패시킨 뒤 원본 OSM outer member ID 기반 키로 수정했어요.
  기존 적재 행도 다각형 동등성으로 매칭해 PK를 보존하며 키를 갱신했어요.
