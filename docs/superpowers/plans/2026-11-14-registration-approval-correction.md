# 회원가입 승인 흐름 정정

사용자 확인: 관리자·총관리자가 있으며 관리자는 회원가입 정보 입력 → 공원 검색·지정 → 가입 신청 제출 → 총관리자 가입 승인 → 로그인 순서다. 이전 공원 개별 신청 흐름을 대체한다.

## 구현 선택
- 계정과 담당 공원을 POST /auth/register {loginId,password,name,phone,email,catalogId} 한 번에 제출한다. 등록과 공원 지정은 한 트랜잭션이다.
- 관리자당 공원 하나인 기존 users/parks 관계의 심사 상태를 가입 승인 원천으로 사용한다. 불필요한 중복 상태 컬럼과 데이터 마이그레이션은 추가하지 않는다. registrationStatus 응답을 명시하고 parkStatus는 호환용으로 유지한다.
- 공원 카탈로그 검색만 공개한다. 담당자·가입 신청·업무 데이터는 공개하지 않는다.
- 승인 전과 반려 계정은 JWT 발급 및 기존 토큰의 업무 API 접근을 모두 차단한다. 총관리자는 기존 콘솔 생성 방식만 허용한다.
- GET /admin/registrations는 신청자 이름·아이디·이메일·전화번호와 지정 공원을 제공한다. 승인·반려 URL은 신청자 userId 기준이다.
- 가입 승인은 로봇 배정을 필수로 요구하지 않는다. 선택적으로 robotIds를 함께 전달할 수 있다.
- 프론트는 한 컴포넌트의 메모리에서 입력·공원 선택 단계를 유지한다. 다음 버튼은 서버 쓰기를 하지 않는다. 공원 확정 시에만 제출하고 비밀번호를 지운다. 자동 로그인하지 않는다.
- 총관리자 관리 UI, 승인 알림 전송, 운영 DB 데이터 수정은 범위 밖이다. 기존 공원 미지정 계정은 담당자 문의를 안내한다.

## 검증 및 진행
- [x] 서버 HTTP+SQLite 회귀 테스트 RED→GREEN: 공개 검색, 원자적 가입, 없는 공원/중복, 승인 전 로그인·기존 토큰 차단, 승인·반려 권한, 로봇 없이 승인, 승인 후 순찰 저장 및 재로그인.
- [x] 프론트 테스트 수정 RED→GREEN: 가입 신청에 공원 포함, 승인 전 로그인 거부, 승인 후 설정 완료 보존.
- [x] 프론트 단계·가입 API 및 서버 공개 검색·승인 API 연결.
- [x] API_SPEC/AUTH/ADMIN/PARKS 및 앱 실행 문서 정정.
- [x] 최종 전체 검사·웹 번들·독립 리뷰.

최종 결과: 서버 전체 테스트 106개 통과, 프론트 회귀 테스트 8개 통과, npm run check 통과(기존 경고 4개), 변경 서버 파일 Ruff 통과, 웹 Exported: dist 확인. CUA 브라우저 검증은 이전 URL 식별 제한으로 수행하지 않음. 운영 DB나 기존 계정 데이터는 변경하지 않음.

로컬 전용 구버전 테스트도 새 계약에 맞게 준비 데이터와 기대 결과를 수정했으며, 신규 회귀 테스트는 저장소의 test_*.py 제외 규칙에 걸리지 않는 server/tests/registration_approval_test.py에 보관한다. 기존 테스트 제외 정책은 유지한다.

독립 리뷰: 중요 결함 없음. 기존 공원당 승인 관리자 한 명 제약을 유지한다. 이 제약은 여러 담당자의 같은 공원 운영을 별도 요구할 경우 재검토해야 한다.
