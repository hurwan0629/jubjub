// 톤 = "옅은 배경 + 진한 글자" 짝. 배지·알림 아이콘 원에 써요
export const tones = {

  error: { fg: 'error',    bg: 'bgError' }, …
} as const satisfies Record<string, { fg: ColorName; bg: ColorName }>;

as const는 "이 값들은 절대 안 바뀌어요"라는 표시예요. 덕분에 TypeScript가 'text', 'brand' 같은 정확한 이름 목록을 알게 되고, <Text color="brnad">처럼 오타를 내면 바로 빨간 줄이 생겨요.
satisfies는 "모양 검사만 하고, 타입은 그대로 둬" 라는 뜻이에요. 톤의 fg/bg가 실제로 있는 색 이름인지 검사하면서도 'textDone' 같은 정확한 값은 유지돼요.

② request — 서버에 실제로 요청

export async function request<T>(path, init = {}) {
  let res;
  try {
    res = await fetch(`${API_URL}${path}`, { ...init, headers: {
      'Content-Type': 'application/json',
      ...(authToken ? { Authorization: `Bearer ${authToken}` } : null),  // 로그인했으면 토큰 붙이기
      ...init.headers,                                                    // 호출한 쪽 값이 마지막(이김)
    }});
  } catch {
    // fetch 자체가 실패 = 서버에 닿지도 못함 (꺼짐, Wi-Fi 다름)
    throw new ApiError(0, '서버에 연결하지 못했어요…', 'network_error');
  }
  if (!res.ok) {                                          // 200~299가 아니면
    const body = await res.json().catch(() => null);   // 본문이 JSON이 아니어도 안 터지게
    throw new ApiError(res.status, body?.message ?? `GET /x 실패 (500)`, body?.code, body?.details);
  }
  if (res.status === 204) return undefined as T;          // 204 = 성공인데 본문 없음
  return (await res.json()) as T;
}
fetch 실패status 0 · network_error/4xx·5xx서버 message 그대로/204undefined/2xxJSON

ApiError는 서버 에러 형식 {status, message, code, details}를 그대로 담는 클래스예요. 화면은 e instanceof ApiError로 "서버가 보낸 에러인지" 구별하고, e.code === 'account_exists'처럼 코드로 분기해요.

③ mockResponse — 진짜 서버인 척

export function mockResponse<T>(data, delayMs = 200) {
  return new Promise((resolve) => setTimeout(() => resolve(structuredClone(data)), delayMs));
}

0.2초 기다리는 이유: 진짜 네트워크처럼 "불러오는 중" 상태를 화면에서 확인하려고. structuredClone(깊은 복사)을 하는 이유: 화면이 받은 객체를 고쳐도 원본 목업이 안 바뀌게 하려고요. 복사 안 하면 화면 A에서 바꾼 값이 화면 B에도 보이는 이상한 일이 생겨요.

리뷰 포인트
  • 토큰이 변수 하나(let authToken, 48줄)에만 있어요. 앱을 껐다 켜면 사라져서 다시 로그인해야 해요. 의도인지 확인 → 유지하려면 SecureStore 같은 안전한 저장소가 필요해요.
  • 401(로그인 만료) 공통 처리 없음. 토큰이 만료되면 각 화면이 알아서 처리해야 하는데, 지금은 공원 검색(steps.tsx)만 401 문구를 보여 줘요.
  • 요청 시간 제한(timeout)이 없어서 서버가 응답을 안 주면 무한정 기다려요.
  • ApiResource에 'settings'가 있는데 서버에는 아직 없어요(정상). 목록과 server/ 문서를 같이 관리하는 규칙만 있으면 돼요.

5hooks/ — 데이터를 화면에 붙이는 층

결론: 거의 모든 훅은 useApi 한 줄 감싸기예요. 예외는 useParkSearch(입력 대기 + 더 보기)와 useKeyboardHeight(키보드 높이)예요.

useApi.ts — 뼈대 (44줄)

export function useApi<T>(fetcher, deps, { refreshMs } = {}) {
  const [state, setState] = useState({ data: undefined, error: undefined, loading: true });
  const [reloadKey, setReloadKey] = useState(0);      // 숫자를 올리면 다시 불러옴

  useEffect(() => {
    let alive = true;                                  // ① 이 effect가 아직 유효한가?
    const load = () => fetcher().then(
      (data) => alive && setState({ data, error: undefined, loading: false }),
      (error) => alive && setState((prev) => ({ ...prev, error, loading: false })), // ② 실패해도 이전 data는 유지
    );
    load();
    const timer = refreshMs ? setInterval(load, refreshMs) : undefined; // ③ 폴링
    return () => { alive = false; if (timer) clearInterval(timer); }; // ④ 정리
  }, [...deps, reloadKey, refreshMs]);

  const reload = useCallback(() => setReloadKey((k) => k + 1), []);
  return { ...state, reload };
}

① alive 플래그가 왜 필요한가 (예시)

  1. 알림 화면에서 "전체" 필터 → 요청 A 출발 (응답까지 0.5초)
  2. 0.1초 뒤 "로봇 오류" 필터 → effect 정리(alive=false) → 요청 B 출발
  3. 요청 B가 먼저 도착해서 "로봇 오류" 목록을 그림
  4. 요청 A가 늦게 도착 → alive가 false라 무시. 없으면 "전체" 목록으로 덮어써지는 버그가 생겨요.

④ 정리 함수(cleanup)

화면을 떠나면 setInterval도 멈춰야 해요. 안 멈추면 안 보이는 화면이 5초마다 계속 서버를 부르고, 이미 사라진 화면의 상태를 바꾸려고 해요.

리뷰 포인트 (useApi)
  • 다시 불러올 때 loading이 true로 안 돌아가요. 처음만 true예요. 그래서 알림 필터를 바꾸면 새 결과가 올 때까지 이전 필터의 목록이 잠깐 보이고, "빈 안내" 판단(!loading)도 이전 값 기준이에요. 필터를 바꿀 때 setState(s => ({...s, loading:true}))를 넣을지 논의해 볼 만해요.
  • 실패 시 이전 data를 유지(②)하는데 화면은 error를 거의 표시하지 않아요 → "오래된 값"인지 사용자가 몰라요.
  • deps는 호출하는 쪽이 책임지고, ESLint의 additionalHooks: (useApi)가 빠짐을 경고해 줘요. 좋은 장치예요.

useParks.ts — useParkSearch (70줄, 가장 까다로운 훅)

하는 일: ① 타이핑이 0.3초 멈추면 검색 ② 20개씩 "더 보기" ③ 늦게 온 응답 무시.

const q = query.trim();
const [typed, setTyped] = useState(q);          // "확정된" 검색어
useEffect(() => {                                // ① 디바운스
  const t = setTimeout(() => setTyped(q), 300);
  return () => clearTimeout(t);                   // 0.3초 안에 또 치면 이전 예약 취소
}, [q]);

useEffect(() => {                                // ② typed가 바뀌면 첫 페이지 검색
  if (!typed) return;
  let alive = true;
  searchParks(typed).then(items => alive && setState({ key: typed, items, hasMore: items.length === 20, … }));
  return () => { alive = false };
}, [typed]);

const current = !!typed && state.key === typed;     // ③ 지금 결과가 지금 검색어의 결과인가?
return { items: current ? state.items : [], loading: !!q && (!current || q !== typed), … };
타임라인 예 ("한강" 입력):
0ms "한" → 300ms 예약 · 120ms "한가" → 이전 예약 취소, 새 예약 · 200ms "한강" → 취소, 새 예약 · 500ms typed="한강" → 서버 요청 1번.
디바운스가 없으면 요청이 3번 나가요.

loading 계산: 입력 칸 값(q)과 확정 검색어(typed)가 다르거나(아직 0.3초 안 됨), 결과의 key가 지금 검색어가 아니면 "찾는 중". 이렇게 하면 타이핑 중에 이전 결과가 깜빡이지 않아요.

hasMore: 받은 개수가 정확히 20이면 "더 있을 수 있음". (딱 20개뿐이면 "더 보기"를 눌러도 빈 결과 — 흔한 단순화예요.)

리뷰 포인트loadMore 안의 searchParks(...).then에는 alive 보호가 없어요. 대신 s.key === typed로 "같은 검색어일 때만 붙이기"를 해서 대부분 안전하지만, 화면을 떠난 뒤 응답이 오면 사라진 화면에 setState를 시도해요(React 19에서는 경고 없음, 실질 영향 작음).

useKeyboardHeight.ts

키보드 높이를 숫자로 알려 줘요. iOS는 "올라오기 시작할 때"(keyboardWillShow), 안드로이드는 "다 올라온 뒤"(keyboardDidShow)만 알려 줘서 둘을 나눠 들어요. 왜 직접 만들었나? 안드로이드 edge-to-edge(화면 끝까지 그리기)와 모달 안에서는 RN 기본 부품 KeyboardAvoidingView가 동작하지 않아서예요. AuthLayout, SignUpEmailScreen, BottomSheet가 써요.

ParkMapSchematic.tsx — 그림 지도 (좌표 ↔ 픽셀 변환)

Figma의 한강공원 그림(390×500)을 깔고, "그림이 공원 범위를 그대로 덮는다"고 가정해서 비율로 위치를 바꿔요.

좌표 → 그림 위치 (toBoundsRatio)
가로 비율 fx = (내 경도 − 왼쪽 경도) ÷ (오른쪽 경도 − 왼쪽 경도)
세로 비율 fy = (위쪽 위도 − 내 위도) ÷ (위쪽 위도 − 아래쪽 위도) ← 위도는 위로 갈수록 커지는데 화면 y는 아래로 갈수록 커져서 "위쪽에서 뺀다"

예: 범위 왼쪽 126.92 ~ 오른쪽 126.94, 아래 37.52 ~ 위 37.54, 내 점 (37.535, 126.925)
fx = (126.925 − 126.92) ÷ 0.02 = 0.005 ÷ 0.02 = 0.25 → 그림 폭 390px × 0.25 = 97.5px
fy = (37.54 − 37.535) ÷ 0.02 = 0.005 ÷ 0.02 = 0.25 → 그림 높이 500px × 0.25 = 125px
→ 왼쪽에서 97.5px, 위에서 125px 지점에 마커를 그려요.

꾹 누른 위치 → 좌표 (확대 되돌리기)

// 그림은 가운데를 기준으로 zoom배 커져 있음. 누른 점을 "확대 전" 위치로 되돌려요
const cx = (at.x - ox - left - contentW / 2) / zoom + contentW / 2;
const cy = (at.y - oy - contentH / 2) / zoom + contentH / 2;
예: 그림 폭 390, 가운데 x = 195, zoom = 2배. 상자 안에서 x = 295를 눌렀어요.
① 가운데로부터 거리: 295 − 195 = 100px
② 2배 확대된 상태이니 원래 거리는 100 ÷ 2 = 50px
③ 다시 가운데 기준으로: 195 + 50 = 245px → fx = 245 ÷ 390 ≈ 0.63
(ox, oy = 상자의 화면 위치, left = 상자가 그림보다 넓을 때 양옆 여백)

그다음 fromBoundsRatio로 좌표를 만들고, 그림 밖(fx·fy가 0~1을 벗어남)이거나 공원 경계 밖이면 onLongPressOutside를 불러요.

리뷰 포인트 (지도)
  • 그림 지도는 어떤 공원이든 한강공원 그림을 써요. 반포·뚝섬을 골라도 같은 그림 위에 비율로 마커를 찍어요. 웹·Expo Go용 대체품이라 괜찮지만, 시연 때 오해 없게 알아 두기.
  • 그림 지도는 공원 경계(다각형)를 그리지 않아요. 네이버 지도는 그려요. 어디까지 찍을 수 있는지 그림 지도에서는 안 보여요.
  • focus/view를 처음 한 번만 정해요(마커가 튀지 않게). 그래서 나중에 추가한 지점이 처음 범위 밖이면 그림 지도에서는 그림 밖으로 나갈 수 있어요.
  • 네이버 지도의 zoomIn은 camera.current가 있어야 동작해요. 카메라가 한 번도 안 움직였으면 첫 버튼이 무시될 수 있어요(초기 onCameraChanged 호출 여부 확인 필요).

광선 교차법을 쉽게

하버사인 공식을 쉽게

지구는 공처럼 둥글어서 위도·경도 차이를 그냥 빼면 거리가 안 나와요. 하버사인은 "공 표면 위 두 점 사이 최단 거리"를 구하는 공식이에요. 코드에서는 지구 반지름 R = 6,371,000m를 쓰고, 각도를 라디안(× π ÷ 180)으로 바꿔 계산해요. 예: 위도만 0.001° 다르면 약 111m (지구 둘레 약 40,000km ÷ 360° ≈ 111km/도 → 0.001도 ≈ 111m).

function RouteEditor({ initial, onDone }) {
  const [draft, setDraft] = useState(initial);       // ← initial은 처음 한 번만 쓰임
  const timers = useRef([]);
  useEffect(() => () => timers.current.forEach(clearTimeout), []);  // 떠날 때 타이머 전부 취소
  const later = (fn, ms) => timers.current.push(setTimeout(fn, ms));

  const handleSave = async () => {
    setSaving(true);
    try {
      await saveRouteConfig(draft);
      setToast(`경로를 저장했어요 · ${next} 순찰부터 적용돼요`);
      later(onDone, 1600);                         // 1.6초 토스트 보여 주고 뒤로
    } finally { setSaving(false); }                 // ← catch가 없음!
  };
}

왜 화면을 둘로 나눴나? useState(initial)은 처음 그릴 때만 initial을 써요. 데이터가 오기 전에 편집기를 만들면 draft가 undefined로 시작해 버려요. 그래서 "데이터가 왔을 때 편집기를 처음 만든다"로 순서를 보장했어요.

타이머를 ref에 모으는 이유: 토스트 1.6초 / 경고 2.5초 뒤에 무언가를 하는데, 그 전에 화면을 나가면 사라진 화면에서 실행돼요. 모아 두었다가 떠날 때 한 번에 취소해요.

저장 버튼은 saving || !!toast || points.length === 0일 때 꺼져요 → 저장 중·저장 직후·지점 0개면 못 눌러요(두 번 저장 방지).

🔴 리뷰 포인트: 저장 실패를 알려 주지 않아요handleSave(RouteEditScreen.tsx:76-86)에 catch가 없어서, 서버 저장이 실패하면 ① 사용자에게 아무 표시 없이 버튼만 다시 켜지고 ② 처리 안 된 Promise 오류(unhandled rejection)가 생겨요. → catch (e) { setToast(null); setError(…) } 추가 제안.

const r = (size - ring) / 2;      // (142 - 24) / 2 = 59  ← 고리 가운데 선의 반지름
const c = 2 * Math.PI * r;          // 원둘레 = 2 × 3.14 × 59 ≈ 370.7
// 재질마다: 길이 = (개수 / 합계) × 원둘레,  시작 위치 = 앞 재질 길이의 합
strokeDasharray={`${len - gap} ${c}`}   // "len만큼 그리고, 원 한 바퀴만큼 비우기" → 한 조각만 보임
strokeDashoffset={-offset}               // 그 조각을 앞 조각 끝에서 시작
transform={`rotate(-90 …)`}             // 12시 방향에서 시작 (기본은 3시)
예: 페트 10, 캔 7, 종이 5, 일반 2 → 합계 24
페트 길이 = 10 ÷ 24 × 370.7 ≈ 154.5 (그리기는 2 빼고 152.5 → 조각 사이 틈) · 시작 0
캔 길이 = 7 ÷ 24 × 370.7 ≈ 108.1 · 시작 154.5
종이 = 5 ÷ 24 × 370.7 ≈ 77.2 · 시작 262.6 / 일반 = 2 ÷ 24 × 370.7 ≈ 30.9 · 시작 339.8 → 합 370.7 = 한 바퀴 ✓

시간대 막대: height: count × 14px → 7개면 98px (Figma "7개 = 98px" 주석).
